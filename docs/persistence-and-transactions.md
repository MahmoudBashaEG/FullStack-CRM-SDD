# Persistence and transactions

- One request = one scoped `CrmDbContext`, shared by handlers, repositories and `EfUnitOfWork`.
- **Worker transactions (SLA-001):** `RunSlaAutomationCommand` is not transactional; for every (rule, ticket, kind) it calls `ExecuteInTransactionAsync` itself so one failure (409, deadlock) rolls back only that item. The unique execution key `UX_AutomationRuleExecutions_RuleTicketKind` makes a replayed item insert nothing twice.
- **Default (single save):** the handler stages Add/Update/Remove and calls `IUnitOfWork.SaveChangesAsync` exactly once. EF Core's implicit transaction makes it atomic. No explicit transaction, no marker.
- **Knowledge Base (KB-001):** `KnowledgeArticles.Version` is a shadow rowversion (overlapping saves ⇒ 409). `UX_KnowledgeCategories_Name` and `UX_TicketKnowledgeArticleLinks_TicketArticle` are in `EfUnitOfWork.KnownUniqueIndexes` (duplicate ⇒ 409). Every command saves once; none is transactional.
- **Optimistic concurrency:** entities with a row version (first: `Tickets.Version`) — `EfUnitOfWork.SaveChangesAsync` turns `DbUpdateConcurrencyException` into `ConflictException` (409); nothing is saved. Aggregate-owned child rows (ticket activity) are inserted in the same single save, so no `ITransactionalCommand` is needed. `AgentTasks.Version` is also exposed as an ETag and checked against `If-Match` before the change (DASH-002). Unique-index violations become `ConflictException` only for the allow-listed business indexes in `EfUnitOfWork.KnownUniqueIndexes`; others stay 500.
- **Multi-step writes:** the command implements `ITransactionalCommand`. `TransactionBehavior` (innermost pipeline behavior) calls `IUnitOfWork.ExecuteInTransactionAsync`, which runs the handler inside the SQL Server execution strategy -> `BeginTransactionAsync` -> handler -> final `SaveChangesAsync` -> `CommitAsync`. Any exception or cancellation -> `RollbackAsync` and rethrow; nothing commits early. Nested transactional commands join the outer transaction.
- **Idempotent single-statement writes:** `TaskReminderRepository.IssueDueAsync` (one `INSERT … SELECT … NOT EXISTS` with `UPDLOCK` / `HOLDLOCK`), `MarkReadAsync` and `TransferUnreadAsync` (`ExecuteUpdateAsync`) are atomic, conditional statements that bypass the change tracker.
- **Write-time authorization:** commands whose permission depends on another aggregate's current state (ticket assignment, collaborator membership) are `ITransactionalCommand`s that read that state through `ITicketAccessLock` (`UPDLOCK, HOLDLOCK, ROWLOCK`) and write before commit. Plain reads never block under `READ_COMMITTED_SNAPSHOT`, so lock hints are mandatory for such checks. Lock order: `Tickets` → `TicketCollaborators` → `AgentTasks`.
- **Retries:** `EnableRetryOnFailure` is on. Explicit transactions go through `ExecuteInTransactionAsync`: each attempt clears the change tracker, opens a transaction and re-runs the whole handler, so handlers of `ITransactionalCommand`s must be replay-safe (no instance state, no external calls, no swallowed DB exceptions). A failure before commit is rolled back and retried; a failure **during** commit is never retried — it surfaces as `CommitOutcomeUnknownException` (503) and the client reloads. `ExecuteSql*` / `ExecuteUpdate` outside a transaction are not assumed to be retried by EF; wrap them in `CreateExecutionStrategy().ExecuteAsync` only when the statement is idempotent.
- **Identity writes:** `UserManager` saves immediately on the scoped `CrmDbContext`, so inside an `ITransactionalCommand` its writes join the transaction. Commands that must keep a write after throwing (login failure counter) are not transactional; commands that must commit a revocation while rejecting (refresh-token reuse) return a result instead of throwing. Writes spanning Identity and CRM rows (signup + customer profile; linked customer name/phone sync) are `ITransactionalCommand`s for the same reason.
- **Administration (ADMIN-001):** `CreateAgentCommand` and `SetAccountStatusCommand` are `ITransactionalCommand`s. Identity saves, session revocation and the `AdminAuditLogs` insert commit together. `SetAccountStatusCommand` locks the target `AspNetUsers` row (and all SuperAdmin rows when deactivating a SuperAdmin) with `UPDLOCK, HOLDLOCK` through `IAccountAdministration`. Settings + audit is one save; `OrganizationSettings.Version` is a rowversion ETag.
- **Queries** never open write transactions (`TransactionBehavior` passes them through; prefer `AsNoTracking` in future query repositories).
- **Ownership:** contract in `Crm.Application/Abstractions/Persistence/IUnitOfWork.cs`; EF implementation in `Crm.Infrastructure/Persistence/EfUnitOfWork.cs`. Controllers and Domain never begin, commit or roll back.
- **Boundary:** atomicity covers one local SQL Server database only. Email/WhatsApp/SMS/payment calls are outside it; a future story needing DB + message reliability must specify an outbox.
- Do not add generic repositories that wrap `DbSet` 1:1; add narrow per-aggregate interfaces only when a feature needs them.
