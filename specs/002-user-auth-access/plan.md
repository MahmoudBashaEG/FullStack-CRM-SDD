# Implementation Plan: User Authentication and Access Control

**Branch**: `master` (active feature: `002-user-auth-access`; no branch created)
**Date**: 2026-10-09 | **Spec**: [spec.md](spec.md)
**Input**: Clarified Feature 002 and the supplied technical planning request. This is proposed design, not implemented behavior.

## Summary

Replace external OIDC with one shared locally managed CRM account store. Infrastructure uses ASP.NET Core Identity for account/password management; a required scalar role enforces exactly Customer, Agent or Admin. The API issues RS256 JWTs and validates them with JwtBearer plus current database account/session state. Angular keeps access tokens in memory, restores authentication through rotating opaque HttpOnly refresh cookies and shares policies with Ticket Management. Admin bootstrap is a protected explicit CLI. Agent account/reference changes are transactional; legacy references and immutable history remain readable.

User-mandated technical choices are JWT Bearer, refresh credentials, established password facilities and the existing stack. Token durations, scalar counting, cookie/CSRF settings, database schema, bootstrap invocation and concurrency details below are technical design choices. They do not broaden the clarified feature.

## Backend Ownership and Use Cases

Use IdentityUserContext<LocalUser,Guid> as the existing CrmDbContext base, call base.OnModelCreating then current configurations. AddIdentityCore supplies UserManager and standard PasswordHasher; deliberately do not add Identity roles or Identity cookie schemes. LocalUser has one non-null AccountRole enum column with SQL CHECK. Reusable ASP.NET role/policy facilities consume exactly one role claim projected from validated current state. This avoids the framework many-to-many role table permitting multiple roles. No custom role-management endpoints or parallel account store.

Application Commands: RegisterCustomer, SignIn, RefreshAuthentication, SignOut, CreateAgent, RenameAgent, SetAgentAvailability, BootstrapInitialAdmin. Queries: CurrentIdentity, ListAgents. Validate at Application boundaries; Identity adapters repeat credential invariants. Password verification and possible rehash use UserManager/PasswordHasher, not controller logic. API supplies cookie/header inputs to commands and writes their transport outputs. Account/session persistence owns explicit transactions; controllers never own business decisions or EF entities.

Transactions use the same scoped context as Identity stores, including framework SaveChanges during CreateAsync. Account creation, role value and AgentReference creation commit together. Rename/availability updates synchronize account/reference in the same transaction. Disable increments AuthVersion, updates SecurityStamp, revokes all its sessions and sets reference ineligible atomically. Re-enable never restores revoked sessions or old versions. Save failures/cancellation roll back all parts; uncertain commit outcomes are not automatically replayed. Preserve existing no EnableRetryOnFailure setting; no new general retry middleware. Propagate CancellationToken to queries/saves/transactions; framework calls without token overload use bounded operations with checks before/after rather than pretending cancellation exists.

Concurrency: agent writes carry explicit version in JSON, with SQL rowversion compare under account writer lock. Stale versions return 409 even for otherwise no-op input. Lock order is account -> its sessions -> linked AgentReference; ticket mutation only locks ticket/reference and never requests an account lock. Refresh/signin/signout lock the account then session/credential; session-only state-check reads never take writer locks. This prevents inconsistent disablement and refresh issuance, while already-authorized operations may finish as specified.

## Credentials, Tokens and Current State

Password length is Unicode scalar count: C# Rune decoding and frontend code-point iteration after rejecting malformed surrogate sequences. Combining marks count separately; no Unicode normalization, trim or truncation. All-space passwords meeting length are allowed by the confirmed policy. Replace/remove Identity's default PasswordValidator (not merely append), disable character-class requirements and use the same validator in all creation paths; frontend must not use UTF-16 maxlength/minlength as authoritative enforcement. Name: trimmed nonblank, up to 200 scalars (technical payload bound). Email: trimmed, syntactically valid single address, maximum 256 UTF-16 units, Identity normalizer NFC+invariant uppercase, used for both username and normalized unique email. Disable conflicting allowed-username character restriction; reject control characters. SQL unique normalized-email index resolves races, with BIN2 collation on canonical values.

Access JWT: RS256, dedicated RSA signing certificate at least 3072 bits, issuer urn:crm:local, audience crm-api, lifetime five minutes capped by session absolute expiry, ClockSkew zero. Require signed tokens, exact algorithm/type/issuer/audience/expiry; MapInboundClaims=false, no external Authority/discovery. Claims: iss,aud,sub (CRM Guid canonical string), role, sid, av (authentication version decimal), jti,iat,nbf,exp. No email/name/password/hash/refresh credential. API loads current account/session on every authenticated request via OnTokenValidated: active account, matching ID/role/version, live non-revoked session, absolute expiry, then attach a trusted per-request identity snapshot for CurrentActor/me. Dependency failure is 503, never authorization success or misleading wrong-credentials 401. No positive auth-state cache. Trade-off: JWT validity is deliberately stateful; database availability is needed for protected operations.

Private signing key stays in an operator-managed certificate store; config references thumbprint/key ID, not private material. Development uses a dedicated CurrentUser/My certificate; production uses an appropriate protected store readable by its host identity. Public prior signing keys may be configured for rollover through the maximum remaining access lifetime; no auto key generation or TLS certificate-key reuse. Required configuration is validated at startup, including expired/missing/inaccessible signing material. Keep data-protection keys durable and protected for antiforgery across restarts; do not commit them. Issuer changes do not redefine stable actor/account identity.

Refresh: 32 random bytes generated by RandomNumberGenerator, Base64Url encoded; store only SHA-256 digest (high-entropy token, not a password), compare with fixed-time primitives. Session family has seven-day absolute lifetime, no sliding extension. Each successful refresh transaction consumes one credential and creates one successor; retains consumed hashes for replay detection until family expiry. Known consumed token replay revokes the whole current family, invalidating its access JWTs; never all other sessions. Unknown/expired/revoked token returns generic 401. No replay grace or retry of a lost response; uncertain delivery may require fresh signin. DB transaction/CAS guarantees one successor.

Cookie __Host-crm-refresh: Secure, HttpOnly, SameSite=Strict, Path=/, no Domain, max-age bounded by session expiry. No JS access or local/sessionStorage token persistence. The supported use is one active tab per cookie/session context; separate browser profiles/devices have independent families. Simultaneous tabs sharing that cookie/session are unsupported. Current-context signout revokes sid so existing access JWTs also fail immediately, clears cookie and memory. Signout without a live cookie is still idempotent; do not revive revoked state. Signin with an existing valid refresh cookie atomically revokes that context before creating the new one. Failed signin leaves existing server context unchanged. Expired-session database records may be purged later by bounded operational maintenance; no new scheduled platform required.

## CSRF, Errors and Abuse Protection

Use built-in IAntiforgery for auth-cookie lifecycle operations plus exact trusted frontend Origin. GET /api/auth/csrf supplies an anonymous request token and HttpOnly antiforgery cookie; signup/signin/refresh omit bearer and signout may include a validated current bearer as a revocation fallback. All cookie-lifecycle antiforgery calls use the same anonymous principal for issuance/validation and restore the trusted principal afterwards. Reject Authorization on csrf/signup/signin/refresh; signout may accept it without bypassing CSRF, as detailed in the authentication contract. These endpoints remain AllowAnonymous only for middleware; refresh/signout validate their own credentials. Fetch request token on startup and after auth transition; keep request token in memory. SameSite and CORS alone are not sufficient. Production same-origin reverse proxy and current development /api proxy are the supported deployment shape; no wildcard credential CORS.

Strict JSON object binding, unknown/duplicate fields rejected, existing ProblemDetails codes/no-store/redaction retained. Bodyless auth mutations still send {} and application/json because current HTTP middleware parses POST bodies. Add explicit 401 challenge/403 forbid mapping rather than relying on default empty JwtBearer bodies. Bearer not authorized ->401; valid Customer/Agent lacking policy ->403. Signup duplicate returns generic registration_failed with no email-specific error; ordinary format errors can identify invalid fields but never credential values. This satisfies non-disclosing failures, not a claim that signup success/failure makes account enumeration impossible.

Technical abuse limits, initially fixed per-process: signin 10/minute and signup 5/minute per remote address; refresh 30/minute per trusted current session/remote address, no attacker-controlled raw token logging; reject excess with 429/retry-after. No persistent lockout or account-existence-based responses. Reverse proxy forwarded headers only from configured trusted proxies. SQL uniqueness conflicts map deliberately to business errors, not blanket 503. Do not log request/response bodies, Authorization, Cookie, password fields, hashes or full Identity validation errors. Wrong/nonexistent/disabled signin follows a standard password-verification work path with a precomputed dummy Identity hash for nonexistent accounts; no account-sensitive error details or claimed perfect constant-time network behavior.

## Agent and Ticket Integration

Each new Agent gets a new Guid AgentReference.Id and nullable LocalUserId link populated with its UserId; unique filtered LocalUserId index. Keep legacy Issuer/Subject columns/identity hash for compatibility; new references use fixed namespace urn:crm:local:user and canonical UserId subject. Admin/Customer have no reference. Account rename updates current reference display but never history. Eligibility is effective only when linked account is active Agent and reference eligible, checked in reference reads and selected-reference locks; database transaction keeps values synchronized.

Versioned migration adds account/session/bootstrap schema and nullable reference link; leaves every existing reference unlinked, sets its eligibility false and does not change ticket FKs or history. No historical account auto-creation or linking. Rename/disable preserve reference Id and ticket snapshots. Existing category provisioning remains. Retire CLI agent upserts: reject a nonempty agents array and reject mutation of linked AgentReferences; empty/omitted agents allowed for compatible category setup. Otherwise the old provisioner could restore forbidden legacy eligibility or desynchronize local identity. Document this narrow compatibility change and update fixtures; it is required by FR-015, not new administration.

ICurrentActor retains its framework-free interface and Actor value compatibility for the existing ticket schema. Remove its current SupportQueue-only check: it requires a trusted authenticated CRM snapshot for any role; ticket endpoints enforce SupportQueue separately. This lets future Customer features reuse CurrentActor without granting queue access. Populate new actors from the trusted local snapshot: Issuer=urn:crm:local:user, Subject=UserId canonical string, DisplayName=current name. Legacy Issuer/Subject history remains unchanged. Stable UserId is the semantic identity; future modules must use it, not external subjects. Do not require a breaking migration of existing actor snapshots.

## Angular and OIDC Retirement

Core AuthService owns one memory token/current identity, initializing/authenticated/anonymous/unavailable state, within-instance session generation and one shared in-flight refresh. Initialization fetches CSRF then uses the same refresh path through transport that bypasses bearer retry interception; success loads /me before guards settle. Any failure clears JWT/current identity: missing/invalid refresh401 becomes anonymous, network/503 becomes unavailable with explicit recovery and no authenticated state. Customers land on identity/access page; Agents/Admins on tickets; Admin also sees Agent management. Signup success goes to signin without automatic authentication.

Interceptor attaches bearer only to same-origin /api segment, excluding public/cookie auth endpoints except optional current bearer on signout. On token-expired401, join the single in-flight refresh operation and replay each protected request at most once with the resulting current JWT, provided its account/session generation is unchanged. If another request already renewed the JWT, reuse that token instead of rotating again. Never refresh/retry signin/refresh/signout,403,409 or network-failed mutations; refresh uses an interception-bypassing transport. Server401 precedes endpoint mutation, so one replay of that rejected request is safe; uncertain completed mutations are never automatically retried. Non-expiry invalid/revoked authentication clears auth without refresh. Any failed refresh, including401/503/network/malformed response or failed identity restoration, clears memory JWT and current-user/role state consistently, rejects all waiters and stops queued replay. Preserve safe diagnostic distinction:401 means anonymous/signin required,503/network means unavailable with explicit user recovery, never a retained authenticated identity. Cleared browser state does not claim successful server-side revocation on network failure. Guards use shared policies; backend remains the security boundary.

Project decision: one active browser tab per signed-in session. Multiple simultaneously active tabs sharing the same authentication session are outside the supported scope of this feature. Cross-tab authentication synchronization is out of scope: no Web Locks dependency, BroadcastChannel requirement or cross-tab locking infrastructure. Within one Angular application instance, AuthService owns exactly one shared in-flight refresh operation. Concurrent expiry-triggered API requests join that operation rather than issuing separate /refresh calls. Publish the new memory JWT before resolving waiters; each eligible waiting request may replay once with the new JWT. Late failures from requests carrying an older JWT reuse an already-renewed current JWT rather than starting redundant rotation. Any refresh failure clears JWT/current identity and completes all waiters with failure; no automatic refresh/replay loop. Keep within-instance session generations so signout or a new signin invalidates stale refresh completions and prevents queued requests from executing under a different identity. PG-001 is resolved by this intentional single-tab scope simplification; no synchronization fallback is required.

Retirement inventory: replace Crm.Api/Authorization/AuthenticationConfiguration.cs external Authority/Testing RSA adapter; replace queue-claim policy and CurrentActor mapping; remove oidc-client-ts, environment.oidc, auth/callback routing, UserManager sessionStorage persistence, auth.e2e token injection. Update current auth/HTTP tests and E2E run-e2e.mjs plus tests/scripts external HTTPS issuer fixtures to real local accounts/sessions with ephemeral signing certificates. Keep 401 categories readiness and launcher/proxy/Development migrations. Update current docs/development/core-ticket-management.md to shared auth setup after implementation; keep all Feature001 specs, plans and validation evidence historical, adding links rather than rewriting past outcomes. No competing external scheme stays enabled, even in Testing. Existing test-auth config prohibition can remain as a rejection guard; test fixtures use production local mechanism with isolated configuration.
